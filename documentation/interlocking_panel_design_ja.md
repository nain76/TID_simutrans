# 信号連動盤（外部制御盤）設計書 — 駅扱い再現機能

状態: 設計ドラフト v0.1
対象: TID_simutrans（OTRP v50 系）

---

## 1. 目的

駅の場内信号・出発信号と前後のポイント（分岐器）を、**外部の連動盤**（PC 上の GUI または物理パネル）から
信号扱者が操作できるようにし、「進路を構成 → 信号現示 → 列車進入 → 進路解除」という駅扱いを Simutrans 上で再現する。

### 要件

| # | 要件 |
|---|------|
| R1 | 指定した信号を「てこ扱い（手動）」にでき、進路が設定されるまで停止現示を保つ |
| R2 | 扱者が進路（どの番線に入れるか／どの線へ出すか）を選ぶと、列車はその進路を通る |
| R3 | 敵対進路は同時に設定できない（連動鎖錠） |
| R4 | 列車の通過に応じて進路が自動で解除される（進路区分鎖錠に相当） |
| R5 | 外部 GUI／物理盤から操作でき、軌道回路の在線・信号現示・進路状態がリアルタイムで盤に表示される |
| R6 | マルチプレイ（ネットワークゲーム）でも同期ずれ（desync）を起こさない |
| R7 | 既存の自動運転（通常信号・選択信号）と同じ路線内で共存できる |

---

## 2. 前提：Simutrans の仕組みと実際の鉄道との対応

Simutrans には**ポイントという独立したオブジェクトが存在しない**。分岐タイルでは、各編成が
自分の経路（`route_t`）に従って進む方向を決めるだけである。したがって本設計では次のように対応させる。

| 実際の鉄道 | 本設計での表現 |
|---|---|
| ポイント（定位／反位） | 進路が通る**分岐タイルと出口方向**（仮想ポイント）。盤上の表示用に定義する |
| 進路 | 始点信号のタイルから着点（次の信号／番線の停止位置）までの**タイル列** |
| 進路設定＝ポイント転換＋鎖錠 | 進路のタイルを連動装置が**鎖錠**し、他の列車が予約できないようにする |
| 信号現示 | 列車が信号に接近したとき、設定済みの進路が自分に有効なら緑にする |
| 列車がポイントに従って進む | 信号を通過する時点で、その編成の経路を**進路のタイル列に置き換える** |
| 軌道回路 | タイルのグループ。車両がいる／予約済みなら「在線」 |
| 進路区分鎖錠 | 列車の後尾が通過したタイルから順に鎖錠を解く |

経路を置き換える処理は既存の**選択信号**（`rail_vehicle_t::is_choose_signal_clear()`、
`vehicle/simvehicle.cc`）がすでに行っているので、その処理をほぼそのまま流用できる。

基本原則: **外部から来る操作はすべてツール（`tool_t`）に変換して実行する**。
ツールはネットワークゲームでは `nwc_tool_t` としてサーバ経由で全クライアントの同じ sync_step に実行されるため、
同期ずれが起きない（R6）。ブリッジは**ゲーム状態を直接書き換えず、読むだけ**にする。

## 4. ゲーム内部の設計

> **方針（§11 参照）**: 連動装置のコードはすべて新規ディレクトリ `interlocking/` に置き、
> OTRP 本体の既存ファイルには**数行の「フック呼び出し」だけ**を入れる。既存クラスのメンバー・セーブ形式・GUI は変更しない。

### 4.1 てこ扱い信号（手動信号）

- **信号オブジェクト（`roadsign_t`）には手を加えない。** どの信号をてこ扱いにするかは、
  連動装置マネージャが「信号の座標の集合」として持つ。
  - 既存の通常信号・選択信号をそのまま使える。pak（信号の画像データ）を作り直す必要もない。
- てこ扱いの登録・解除は外部盤（または `TOOL_INTERLOCKING` のコマンド）から行う。ゲーム内の信号ウィンドウは変更しない。
- 「自動扱い（てこ扱いを一時的に外す）」モードも持たせる。夜間無人運転のように、扱者がいないときは
  既存の信号動作に戻せるようにする（R7、デッドロック回避）。

### 4.2 連動装置マネージャ `interlocking_manager_t`（新規）

`karte_t` のメンバーにはせず、`interlocking/` 内のシングルトン（`interlocking_manager_t::get()`）として持つ。

```cpp
struct il_point_t {          // 仮想ポイント（盤の表示用）
    koord3d pos;             // 分岐タイル
    ribi_t::ribi normal;     // 定位の出口方向
    ribi_t::ribi reverse;    // 反位の出口方向
};

struct il_route_t {          // 進路
    uint16  id;
    plainstring name;        // 例 "1R→2番線"
    koord3d start_signal;    // 始点（てこ扱い信号）
    koord3d end_pos;         // 着点（番線の停止位置 or 次の信号の手前）
    vector_tpl<koord3d> tiles;            // 定義時に経路探索で確定させたタイル列
    vector_tpl<std::pair<uint16,bool>> points; // 通過する仮想ポイントと定位/反位
    vector_tpl<uint16> conflicts;         // 敵対進路（自動計算＋手動追加）
    bool is_departure;       // 出発進路か場内進路か（表示用）
    uint8 release_mode;      // 0=通過で自動解除, 1=扱者が取り消すまで保持（てこ反位保持）
};

enum il_route_state_t {
    IL_IDLE,       // 定位（未設定）
    IL_SET,        // 進路設定済み・鎖錠中・列車待ち（信号は停止→接近で進行）
    IL_OCCUPIED,   // 列車が進路に進入した
    IL_RELEASING,  // 取消要求中（接近鎖錠の時素待ち）
};

struct il_station_t {        // 連動駅（1 つの連動盤の単位）
    uint16 id;
    plainstring name;
    halthandle_t halt;       // 対応する駅（任意）
    uint8 owner;             // プレイヤー番号。操作権限の判定に使う
    vector_tpl<il_route_t> routes;
    vector_tpl<il_point_t> points;
    vector_tpl<il_track_circuit_t> circuits;  // 軌道回路（タイルのグループ）
};
```

実行時の状態（セーブ対象）:

- `route_state[route_id]`、進路を占有している編成 `convoihandle_t`
- 鎖錠中のタイル集合（`koord3d → route_id` のハッシュ）。**`schiene_t` にはビットを追加しない。**

#### 連動区域の制約（フックを減らすための前提）

**連動区域（進路のタイル）に入る入口は、すべててこ扱い信号にする**ことを運用ルールとする。
こうすると、区域内に入れる列車は必ずマネージャの判定を通るので、
自動信号の列車が鎖錠中のタイルを予約しないよう `block_reserver()` に手を入れる必要がなくなる。
マネージャは進路を設定するときと解除するときに、この制約が守られているか（区域の入口にてこ扱いでない信号や
分岐がないか）を検査し、守られていなければ盤に警告を出す。

### 4.3 進路の定義（作るとき）

1. 扱者（またはプレイヤー）は始点のてこ扱い信号と着点タイルを指定する（ゲーム内の 2 クリックツール、または外部 GUI から）。
2. 既存の `route_t::find_route()` で始点→着点の経路を探し、得られたタイル列を**そのまま固定して保存する**。
   経由タイルを追加で指定できるようにすれば、渡り線経由などの別ルートも定義できる。
3. タイル列から分岐タイル（ribi が 3 方向以上の線路）を抜き出し、仮想ポイントとして登録する。
4. 敵対進路は「タイルを 1 つでも共有する進路」として自動計算する。平面交差（ダイヤモンドクロス）も
   同じタイルなので自動的に含まれる。必要に応じて扱者が手動で追加・削除できる。

### 4.4 進路の設定（てこを引く）

`tool_interlocking_t` のコマンド `set` が実行されたとき:

1. 進路の状態が `IL_IDLE` であること。
2. 敵対進路がどれも `IL_IDLE` であること。
3. 進路の全タイルが「他の進路に鎖錠されていない」かつ「他の編成に予約されていない（`schiene_t::is_reserved()`）」こと。
4. 条件を満たせば全タイルをマネージャの鎖錠集合に登録し、状態を `IL_SET` にする。満たさなければ失敗理由を返す（盤上の「てこ不良」表示）。

### 4.5 列車が信号に接近したとき

`rail_vehicle_t::is_signal_clear()` の先頭に、**3 行のフック**だけを入れる（フック H1）。

```cpp
#ifdef TID_INTERLOCKING
	{ bool il_result; if(  interlocking_hook_signal( this, next_block, restart_speed, call_by_step, il_result )  ) return il_result; }
#endif
```

`interlocking_hook_signal()`（`interlocking/` 内）は、その信号がてこ扱いでなければ `false` を返す。
その場合は既存の処理がそのまま続くので、通常の信号の動作は変わらない。
`block_reserver()`・`get_convoi()`・`access_route()` などは public なので、新規ファイルから呼び出せる。

フック先の処理:

1. マネージャに問い合わせ、この信号を始点とする `IL_SET` の進路を探す。なければ **停止現示（赤）で待機**して終わる。
2. 列車選別（任意）: 進路に「この路線／この編成のみ」の条件があれば確認する。
3. 編成の経路の `start_block` 以降を、進路のタイル列に置き換える。
   着点から先は、時刻表の目的地まで `find_route()` で探し、後ろにつなげる。
   `is_choose_signal_clear()` の「経路を置き換えて全編成（連結相手含む）に反映する」部分と `advance_to_end` の処理を参考に、
   **`interlocking/` 側に同等の処理を書く**（本体の関数をくくり出す改修はしない。コードは重複するが、OTRP 側の差分を増やさないことを優先する）。
4. 着点から目的地に行けない場合（誤った番線を選んだなど）は赤のままにし、盤に「誤進路」警告を出す。
5. `block_reserver()` で進路のタイルを予約する。連動区域の制約（4.2）があるので、他の列車が鎖錠中のタイルを先に予約していることはない。
6. 成功したら `sig->set_state()` で信号を進行（緑）にし、進路を `IL_OCCUPIED`、占有編成を記録する。

### 4.6 進路の解除

- **自動解除（進路区分鎖錠）**: `schiene_t::unreserve()` には手を入れず、マネージャが**ワールドの step ごとに**
  `IL_OCCUPIED` の進路のタイルを読み取り（`get_reserved_convoi()` と車両の在線）、占有編成がもう予約していないタイルを
  鎖錠集合から外す（フック H2）。進路の全タイルが外れたら状態を `IL_IDLE` に戻し、盤に通知する。
  これで後尾が通過した区間から順に、次の進路が設定できるようになる。
  - `karte_t::step()` はネットワークゲームの全クライアントで同じ順序で実行されるので、解除の結果も全員で一致する。
- **扱者による取消**: 列車がまだ進入していなければ取り消せる。列車が信号に接近中（停止できない距離）の場合は
  `IL_RELEASING` にして、一定時間（時素、例えば 30 秒相当の tick）待ってから解除する（接近鎖錠に相当）。
  最初の版では「列車が進入前なら即時解除」だけでもよい。
- **非常解除**: 管理者向けに強制解除コマンドを用意する（既存の「予約解除ツール」相当）。

### 4.7 ツール `tool_interlocking_t`（`TOOL_INTERLOCKING`、simple tool）

既存の `tool_change_roadsign_t` と同じく、`default_param` の文字列でコマンドを受け取る。

| コマンド | 書式（例） | 内容 |
|---|---|---|
| 進路設定 | `set,<station>,<route>` | てこを引く |
| 進路取消 | `cancel,<station>,<route>` | てこを戻す |
| 自動扱い | `auto,<x>,<y>,<z>,<0/1>` | 信号を自動扱いに切り替え |
| 駅定義 | `new_station,<halt_x>,<halt_y>,<name>` | 連動駅を作る |
| 進路定義 | `def_route,<station>,<sx>,<sy>,<sz>,<ex>,<ey>,<ez>[,<経由…>]` | 進路を登録 |
| 進路削除 | `del_route,<station>,<route>` | |
| 強制解除 | `force_release,<station>,<route>` | 管理者のみ |

- 権限: 連動駅の所有者と同じプレイヤー（または公共プレイヤー）だけが実行できる。
- 定義系のデータが長くなる場合は、複数回のツール呼び出しに分割する。

### 4.8 セーブデータ

**セーブ形式のバージョン（`OTRP_VERSION_MAJOR`）は上げない。** 上げると OTRP 本体の更新と番号がぶつかり、取り込みのたびに調整が必要になるため。

- 方式: **セーブファイルの末尾に追記ブロック**を書く（フック H3）。
  - 保存時: 本体のデータをすべて書き終えた後に、マジック番号（例 `'TIDL'`）・独自のバージョン番号・連動装置のデータを書く。
  - 読み込み時: 本体のデータを読み終えた後、`loadsave_t::is_eof()` でなければマジック番号を読み、一致したときだけ連動装置のデータを読む。
    追記ブロックがない古いセーブは、空の状態で始める。
  - 連動装置のデータ形式が変わったら、OTRP の番号ではなく**独自のバージョン番号**を上げる。
  - 改造していない OTRP でこのセーブを開いても、末尾は読まれずに無視されるだけなので、マップ自体は開ける（P0 で要確認）。
- ネットワークゲームでは、途中参加したクライアントもサーバが保存したセーブを受け取るので、追記ブロックも一緒に届く。
- **確認事項（P0 で最初に検証）**: 圧縮形式（zip / bzip2 / zstd）とマルチスレッドの読み込みで、`is_eof()` が末尾を正しく判定できるか。
  判定できない形式があれば、代替案として「本体データの最後のフィールドの直後に固定長のマーカーを書く」方式を検討する。
- `rotate90()` で、保存している `koord3d` と ribi をすべて回転させる（フック H4。忘れるとマップ回転で壊れる）。
- 新しいマップを作るとき・読み込むときはマネージャを空にする（フック H4 と同じ場所）。
- 線路や信号が撤去されたら、関係する進路を「無効」にする（削除はせず盤上で赤表示し、扱者が再定義できるようにする）。

## 5. 外部連携（ブリッジ）

### 5.1 `interlocking_bridge_t`

- 設定は本体の `simuconf.tab`／`settings_t` には追加せず、**独自の設定ファイル `interlocking.tab`**（ユーザーディレクトリ）から読む。
  `port = 0`（0 またはファイルなしで無効）。有効なら **127.0.0.1 のみ**で TCP 待ち受けをする（外部公開しない）。
- ノンブロッキングソケットを、メインループ（`karte_t::interactive()` の `network_check_activity()` 付近）から毎フレーム `select()` する（フック H5、1 行）。
  既存の `network/network.h` のソケット関数を流用する。
- 受信したコマンドは `tool_interlocking_t` の `default_param` に変換して `welt->set_tool()` を呼ぶだけ。
- 状態送信は、購読中の駅について**数フレームごとに差分だけ**送る。読むだけなので同期に影響しない。

### 5.2 プロトコル（JSON Lines：1 行 1 メッセージ）

**クライアント → ゲーム**

```json
{"type":"hello","client":"panel-A","version":1}
{"type":"list_stations"}
{"type":"get_layout","station":3}
{"type":"subscribe","station":3}
{"type":"set_route","station":3,"route":12,"req":101}
{"type":"cancel_route","station":3,"route":12,"req":102}
```

**ゲーム → クライアント**

```json
{"type":"layout","station":3,"tracks":[...],"signals":[...],"points":[...],"routes":[...],"circuits":[...]}
{"type":"result","req":101,"ok":false,"reason":"conflict","with":[9]}
{"type":"route","station":3,"route":12,"state":"set"}
{"type":"signal","pos":[120,45,2],"aspect":"green"}
{"type":"circuit","station":3,"id":"2T","occupied":true}
{"type":"approach","station":3,"signal":"1R","convoy":"普通 523M","line":"本線"}
```

- `set_route` の結果は、ツールが実際に実行された後（ネットワークゲームならサーバから戻ってきた後）に `result` で返す。
  盤側は `req` で対応づけ、それまで「扱い中」表示にする。
- `layout` は盤の自動描画用。タイル座標・線路の向き・信号の位置と向き・仮想ポイントを含む。
- 接近表示（`approach`）は、てこ扱い信号の手前 N ブロック以内に列車が入ったら送る。
  扱者がどの列車をどこに入れるか判断するための情報で、駅扱いの再現には重要。

### 5.3 中継プログラム（任意）

ゲーム本体には TCP + JSON Lines だけを実装し、次のものは外部の小さなプログラム（Python など）に任せる。

- **Web 連動盤**向け: TCP ⇄ WebSocket の変換。ブラウザから直接 TCP にはつなげないため。
- **物理盤**向け: シリアル（Arduino）や GPIO（Raspberry Pi）⇄ JSON の変換。

こうするとゲーム本体の変更を小さく保て、盤の種類を増やしてもゲーム側を触らずに済む。

## 6. 外部連動盤の設計

### 6.1 Web 連動盤（PC）

- `layout` から駅の配線略図を自動で描く（SVG）。手作業で見やすく配置できるよう、盤ごとのレイアウト JSON で座標を上書きできるようにする。
- 表示:
  - 軌道回路: 在線＝赤、進路鎖錠中＝白（または黄）、何もなし＝消灯
  - 信号: 停止＝赤、進行＝緑
  - ポイント: 定位／反位の向き
  - 接近表示ランプと列車名（列番）
- 操作は次の 2 方式から選べるようにする。
  - **進路てこ方式**: 進路ごとにてこ（ボタン）を並べる。小駅向き。
  - **着点ボタン方式**: 始点ボタン→着点ボタンの順に押すと、その組み合わせの進路を選ぶ（継電連動盤の方式）。
- 失敗時は理由（敵対進路あり／在線あり／誤進路）を表示する。

### 6.2 物理盤

- Arduino：てこ（トグルスイッチ）・押しボタンを入力、LED を出力にして、シリアルで 1 行テキストを送受信する。
  例: `L12=1`（てこ 12 を反位）、`C2T=1`（2T 在線ランプ点灯）。
- 中継プログラムが「てこ番号 ↔ 進路 ID」「ランプ番号 ↔ 軌道回路／信号」の割り当て表を持ち、JSON と変換する。
- 物理てこは位置が残るので、起動時にゲーム側の状態とてこの位置が一致しないときは「不一致」表示にし、
  扱者がてこを戻すまで操作を受け付けない。

## 8. 注意点・リスク

1. **同期ずれ**: ブリッジやGUIからゲーム状態を直接変更しない。必ずツール経由にする。
   乱数・時刻など同期しない値を進路の判定に使わない。
2. **経路の再計算**: 編成は停車後や長時間の停止後に経路を再計算することがある。
   再計算した経路が、扱者が設定した進路と違うタイルを通っても、てこ扱い信号の位置で必ず置き換わるので問題ない。
   ただし、てこ扱い信号の位置より**手前**で別ルートに逸れる経路にならないよう、選択信号と同じく
   「この信号までの経路は変えない」ことをテストで確認する。
3. **デッドロック**: 扱者が進路を設定しないと列車は永遠に止まる。自動扱いへの切り替え（4.1）と、
   盤上の長時間停止警告で対処する。
4. **既存の予約処理との競合**: 長閉塞信号（longblock）・優先信号・連結（coupling）が進路内にある場合の挙動は
   P1 で個別に確認する。最初の版では「進路内にはてこ扱い信号以外の信号を置かない」制限にしてもよい。
5. **性能**: 本体の `block_reserver()` には手を入れない。フック H1 の先頭で「てこ扱い信号か」をハッシュで 1 回引くだけにし、通常の信号の処理コストを増やさない。
6. **連動区域の制約違反**: 区域の入口にてこ扱いでない信号があると、自動信号の列車が鎖錠中の進路に入り込める。マネージャの検査（4.2）で警告し、P1 のテストで必ず確認する。
7. **選択信号の処理の重複**: 経路を置き換える処理を `interlocking/` 側に複製するため、OTRP 側の選択信号が修正されても自動では反映されない。取り込み時のチェック項目に入れる（§11.4）。
6. **セキュリティ**: ブリッジは 127.0.0.1 のみで待ち受け、外部に開かない。リモートの盤を使う場合は中継プログラム側で認証を行う。

## 10. 決定事項

- **ネットワークゲーム対応は必須**とする。
  - 状態の変更はすべて `TOOL_INTERLOCKING` 経由（`nwc_tool_t` でサーバが実行 sync_step を決めて全クライアントへ配信）。
  - サーバ・全クライアントが同じ改造版（同じ OTRP 本体＋同じ連動装置のバージョン）である必要がある。
  - 盤の操作結果はサーバ往復後に返るため、盤側は `req` で応答を待ち「扱い中」表示を出す。
  - 各段階で、2 クライアント接続時に checklist 不一致（desync）が出ないことをテストする。
- **外部ソフトのみでは実現不可**のため、ゲーム本体の改造と新規追加を行う。
  - 既存の GUI・スクリプト API・ネットワーク命令のいずれにも、信号現示や列車経路を外から操作する手段がないため。
  - ゲーム本体は「連動装置」と「外部接続口（ブリッジ）」に限定し、盤の表示・操作は外部ソフトで実装する。

## 11. OTRP 本体への影響を最小にする方針

OTRP 本体が更新されたときに、この機能を**新しい OTRP にすぐ載せ直せる**ことを最優先にする。

### 11.1 基本ルール

1. 連動装置のコードは**すべて新規ディレクトリ `interlocking/`** に置く（マネージャ、ツール、ブリッジ、セーブ処理、経路置き換え処理）。
2. 本体の既存ファイルには、**`interlocking/` の関数を呼ぶ 1〜3 行のフック**だけを入れる。ロジックは書かない。
3. フックはすべて `#ifdef TID_INTERLOCKING` で囲み、行末に `// TID_IL` のコメントを付ける。
   `grep -rn "TID_IL"` で改造箇所を全部見つけられるようにする。マクロを定義しなければ、OTRP とまったく同じ動作になる。
4. 既存クラスのメンバー変数・既存関数の引数・セーブ形式のバージョン・既存 GUI・`simuconf.tab` は**変更しない**。
5. 本体の関数を共通化するリファクタリングはしない。必要な処理は `interlocking/` 側に書く。

### 11.2 本体へのフック一覧（予定）

| ID | ファイル | 場所 | 変更量 | 内容 |
|---|---|---|---|---|
| H1 | `vehicle/simvehicle.cc` | `rail_vehicle_t::is_signal_clear()` の先頭 | 3 行 | てこ扱い信号ならマネージャに判定を任せる |
| H2 | `simworld.cc` | `karte_t::step()` | 1 行 | 進路の自動解除（進路区分鎖錠）、状態変化の検出 |
| H3 | `simworld.cc` | セーブ／ロード処理の末尾 | 2 行 | 追記ブロックの書き込み／読み込み |
| H4 | `simworld.cc` | `rotate90()`、マップの破棄・新規作成 | 2 行 | 座標の回転、状態のクリア |
| H5 | `simworld.cc` | `karte_t::interactive()` のループ | 1 行 | 外部ブリッジのソケット処理（ローカルのみ・状態を書き換えない） |
| H6 | `simmenu.h` / `simmenu.cc` | `SIMPLE_TOOL_COUNT` の直前、ツール生成の `switch` | 各 1〜2 行 | `TOOL_INTERLOCKING` の登録 |
| H7 | `Makefile` / `CMakeLists.txt` / `Simutrans-Main.vcxitems` | ソース一覧 | 数行 | `interlocking/*.cc` の追加と `TID_INTERLOCKING` の定義 |

合計 **既存ファイル 7〜8 個・およそ 20 行**。ゲームの動きに関わるのは H1〜H4 と H6 だけで、残りはビルドと外部接続のための変更。

- H6 の `TOOL_INTERLOCKING` は、ネットワークでツール番号として送られる。サーバと全クライアントが同じ改造版である限り、
  番号が OTRP 側の新しいツールとずれても問題はない。enum の**最後尾**に足すので、OTRP 側の追加とぶつかっても位置を合わせるだけで直せる。

### 11.3 ブランチ運用

- `otrp-upstream`: OTRP 本体をそのまま追いかけるブランチ。
- `tid-interlocking`: その上に**フックのコミット 1 つ**と**`interlocking/` 追加のコミット**を重ねたブランチ。
- OTRP が更新されたら、`otrp-upstream` を更新して `tid-interlocking` をその上に rebase（または merge）する。
  `interlocking/` は新規ディレクトリなので衝突せず、衝突しうるのはフックの約 20 行だけになる。
- フックのコミットは `git format-patch` でパッチファイルとしても保存しておき、手作業で当て直す場合にも使えるようにする。

### 11.4 OTRP 更新を取り込むときのチェック項目

1. `grep -rn "TID_IL"` でフックが全部残っているか（H1〜H7）。
2. フック先の本体関数（`is_signal_clear`、`block_reserver`、`karte_t::step`、セーブ／ロード）の**シグネチャや役割が変わっていないか**。
3. 選択信号（`is_choose_signal_clear`）の経路置き換え処理が変わっていれば、`interlocking/` 側の複製にも反映する。
4. `OTRP_VERSION_MAJOR` が上がっていても、こちらの追記ブロックは独自のバージョン番号なので変更不要。
   ただしセーブの末尾の書き方が変わっていないかは確認する。
5. 自動テスト（P1 で用意）: 小さなテストマップで「進路設定 → 列車進入 → 自動解除」と、セーブ → ロード後に状態が戻ることを確認する。

### 11.5 新しい OTRP 本体への移植キット（例: v57 → v60）

前提となる作業の流れ: v57 に機能を追加して使う → OTRP v60 がリリースされる → **v60 本体に改造を入れ直す**。
この「入れ直し」を、人でも AI でも短時間・確実にできるように、次のものをリポジトリに置く。

1. **`interlocking/PORTING.md`（移植手順書）**
   - フックごとに「どの関数の、どの処理の直前／直後に入れるか」を**行番号ではなく関数名と目印のコード**で書く
     （行番号はバージョンが変わるとずれるため）。
   - 例: 「H1: `rail_vehicle_t::is_signal_clear()` の中、`signal_t *sig = ...find<signal_t>()` と NULL チェックの直後に、次の 3 行を入れる」。
   - 各フックが**何のために必要か**も書く。v60 で関数が分割・改名されていても、役割から入れる場所を判断できるようにするため。
   - そのまま AI に渡せる移植依頼文のテンプレートも含める。
2. **`interlocking/hooks.patch`（フックだけのパッチ）**
   - まずは `git apply --3way` で当ててみる。うまく当たればそれで移植完了、当たらなかった箇所だけ手順書を見て手で入れる。
3. **`interlocking/check_hooks.sh`（確認スクリプト）**
   - `TID_IL` の目印が H1〜H7 の全箇所にあるか、`interlocking/` から呼んでいる本体の関数（`block_reserver` など）がまだ存在するかを確認する。
4. **ビルドで漏れを検出する**
   - フック先の関数を `interlocking/hooks.h` に 1 か所にまとめて宣言する。本体側の関数の引数が v60 で変わっていれば、コンパイルエラーで気づける。
5. **動作確認用のテストマップ**（P1 で用意）
   - 移植後に「進路設定 → 列車進入 → 自動解除」と、ネットワーク 2 クライアントで同期ずれが出ないことを確認する。

移植の手順:

```
1. v60 を取得し、interlocking/ をコピーする
2. hooks.patch を当てる（当たらない箇所は PORTING.md を見て手で入れる）
3. check_hooks.sh を実行して漏れを確認する
4. ビルドする（コンパイルエラー＝本体側の変更点。そこだけ追従する）
5. テストマップで動作を確認する
```
